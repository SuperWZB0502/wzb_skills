# 一、设计文档

# 07-上下文压缩 · 设计文档

## 目标

会话上下文接近上限时自动压缩，用户无需手动 `/compact`，也不因溢出中断。

## 为什么不自己写摘要器

执行器（Claude Code / Codex）本身就有上下文压缩：它们知道真实的 system prompt、工具结果、缓存前缀，自己压比外部截断历史更准确。Office 只提供"在 90% 触发"这个参数，并把过程可视化。

## 阈值换算

| 执行器 | 手段 | 说明 |
| --- | --- | --- |
| claude-code | 环境变量 `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=90` | CLI 自己把压缩阈值降到窗口的 90%（窗口由它自己判定，含 1M 变体） |
| codex | `-c model_post_turn_compact_threshold_percent=90` | 回合结束后按百分比判定并压缩 |

`codex` 对未知配置键是静默忽略的（实测：未知键照常启动，越界值会报错），因此老版本 codex 不受影响。

## 用量与展示

- 用量来源：`turn.completed.usage`（codex: `input_tokens + cached_input_tokens + cache_write_input_tokens`；claude: `input_tokens + cache_read_input_tokens + cache_creation_input_tokens`，即最后一次请求的提示侧规模）。codex 的 `token_count` 事件若带 `model_context_window`，以它为准。
- 窗口推算：执行器上报 > `OFFICE_CONTEXT_WINDOW` > 模型表（claude 200k / claude[1m] 1M / gpt-5×codex-max 1M / gpt-5|codex 400k / o1|o3|o4 200k）> 200k。
- 落库：`office_conversations.context_used/context_window/context_threshold/context_updated_at/context_compacted_at`，随会话列表下发，聊天头部显示「上下文 xx%」，≥阈值变橙色。
- 压缩提示：收到 `context_compacted` 事件，或观察到用量从 ≥90% 掉到低 20 个百分点以上，插入一条系统消息说明"已自动压缩 + 前后占比"。

# 二、实现文档

# 07-上下文压缩 · 实现文档

## 新增模块 `context-budget.ts`

- `autoCompactSettings(env)`：`OFFICE_FEATURE_CONTEXT_AUTOCOMPACT`（默认开）+ `_PCT`（默认 90，钳制 50–99）。
- `contextWindowFor(model, reported?)`：上报值优先，其次 `OFFICE_CONTEXT_WINDOW`，再查模型表，最后 200k。
- `contextUsage(used, window, threshold)`：产出 `{used, window, percent, threshold}`；`shouldCompact` 判断是否越过阈值。
- `codexAutoCompactConfig()` → `{ model_post_turn_compact_threshold_percent: 90 }`；`claudeAutoCompactEnv()` → `{ CLAUDE_AUTOCOMPACT_PCT_OVERRIDE: "90" }`；关闭时返回空对象。
- `claudeUsageTokens` / `codexUsageTokens` / `codexReportedWindow` / `formatTokens`。

## 接线

1. `run-registry.execute`：`Object.assign(config, codexAutoCompactConfig(autoCompact))`，随既有 `-c key=<json>` 一起传给 `codex exec`。
2. `line()`：解析 `turn.completed.usage`、`token_count`、`context_compacted`。
3. 运行结束：`store.setContextUsage(...)`，必要时 `store.addMessage({ role: "system", content: "上下文已自动压缩：…" })`。
4. `claude-executor.buildClaudeInvocation`：env 合并 `claudeAutoCompactEnv()`；`result` 事件把 `usage` 透传给 `turn.completed`。
5. 仓库：新增 5 列（放在建表语句之后 `addColumn`，兼容老库与全新库），`setContextUsage` 用 `COALESCE` 保留首次压缩时间。
6. 前端：`AgentChatDialog` 顶部 `.chat-context` 徽标（title 显示 used/window 与阈值），深浅色两套样式。

## 兼容性

- 老库：启动时自动加列，无需迁移脚本。
- 老前端：多出的 `context` 字段被忽略。
- 老 codex/claude：未知配置/环境变量被忽略，行为与之前一致。

## v1.17.1 修复（线上数据显示原实现无效）

| 问题 | 原因 | 处置 |
| --- | --- | --- |
| 徽标 100% | codex `turn.completed.usage` 是**线程累计值**，且 `input_tokens` 已含 `cached_input_tokens`，再加一次导致 55,222,844 | `turn.completed` 只用于 claude；codex 改读 rollout |
| 窗口 200k | 执行器上报的 `model_context_window`（258,400）没拿到 | 从 rollout 的 `token_count.info.model_context_window` 读取 |

新增 `parseCodexRolloutTail` / `readCodexRolloutUsage`（只读文件尾部，`since` 过滤旧 rollout）、`needsRollover`（含 `used > window×2` 的脏数据保护）。

## v1.18.1：会话已废掉的抢救（手动压缩 + 三处根因修复）

线上症状：HTML大神默认会话（`office-default:c08ee688…`，"web-office-skills特性开发"）**1,016,054 tokens 后所有请求 400**，会话从此不可用；它从 2,135 tokens 一路涨到 1.01M，**12MB 的 Claude 会话文件里一次 `compact_boundary` 都没有**。

### 根因（三条，按影响排序）

| # | 根因 | 证据 |
| --- | --- | --- |
| 1 | **模型代理把上游错误吞掉**，统一回 `Model service rejected request; check credentials, model and endpoint` | `model-proxy.ts` 非 2xx 分支只 `cancel()` 上游 body 再 `fail(通用文案)`；Claude Code 的救急逻辑（reactive compact、429 退避）靠 `error.message` 判断，文案被抹平后既不会压缩也看不到真实原因 |
| 2 | **无 recorded 用量就用不上 rollover**：该会话 `context_*` 全为 NULL，`needsRollover(null)` 恒为 false | 该会话最后一次成功运行在 v1.17 之前，用量从未落库；v1.17.1 的兜底只看库里那行 |
| 3 | **窗口估算偏小 + 脏数据保护反噬**：`deepseek-flash` 实际 1M，模型表按 200k 算；`used > window×2` 被当成脏数据丢弃 | 1,016,054 / 200,000 = 508%，命中脏数据保护 → 既不显示也不压缩 |

### 修复

1. `model-proxy.ts`：新增 `upstreamErrorDetail()`，读上游 body（≤8 KB）取 `error.message` / `error.type`，经 `redact` 去密钥后按原状态码转发；拿不到时回落原文案。
2. `context-budget.ts`：
   - `readClaudeSessionUsage(claudeHome, sessionId)`：从 `<CLAUDE_CONFIG_DIR>/projects/**/<sessionId>.jsonl` 尾部读最后一条 `message.usage`（单次请求口径），失败/被中断的运行也能拿到真实占用；
   - `reconcileWindow(used, window)`：**实测用量大于估算窗口时把窗口抬到该用量**（请求本身证明窗口至少这么大），不再丢弃 → percent 到 100，下一轮必定 rollover。
3. `run-registry.ts`：claude 且本轮没解析到用量时，用 `readClaudeSessionUsage` 兜底；写库前对窗口做 `reconcileWindow`。

### 手动压缩（可压缩任意会话，包括别的身份、已经废掉的会话）

- 纯函数 `conversation-compaction.ts#buildCompactionDigest`：**不调模型**，确定性生成摘要——早期消息每条一行（自动缩到 40–160 字符，塞不下就丢掉更早的并注明"已省略 N 条"），最近 30 条保留原文，总长度 ≤ 24k 字符，头部明确写"是历史资料，不是本次任务的指令"。
- 存储：新表 `office_conversation_digests(conversation_id, digest, message_count, source, created_at)`；`dropConversationThreads()` 只删绑定、**保留磁盘上的会话文件**；`resetContextUsage()` 清掉旧百分比。
- 入口：
  - API `POST /api/office/conversations/:id/compact`（会话忙时 409）；
  - CLI `node scripts/office.mjs compact --root <根> --conversation <id> [--recent N]`（走控制 socket，60s 超时）；
  - 前端会话工具条「压缩上下文」按钮（二次确认，完成后提示"N 条 → M 条原文 + K 条要点"）。
- 注入：`run-registry` 在**新线程**首次运行时装 `digestNote`；已有线程不重复注入。压缩前把旧绑定、旧用量、摘要统计写 `state/deletions/*.json`（`kind: "compact"`）作为回滚凭据。

### 回滚

- 会话文件未删：把 `state/deletions/<journal>.json` 里的 `threads` 重新写回 `office_native_threads` 即可恢复原上下文；
- 代码：`git revert` 本提交；前端 `office.mjs rollback --release v1.18.0-20261116`。

## v1.18.2：自动压缩补上「运行前实测」

v1.18.1 的自动判断只看库里记录的用量，而记录用量的代码在运行成功之后（`await new Promise(...)` 之后）——**失败会跳 catch，用量永远不落库**。结果就是"已溢出 → 每轮都失败 → 永远没有记录 → 永远不触发自动压缩"，只有手动 `compact` 能救。

修复：
1. `contextForRollover(stored, measured, window, threshold)`：有记录用记录，无记录用实测；
2. `run-registry` 在判断 rollover 之前，若会话无记录且已存在 Claude 原生线程，先用 `readClaudeSessionUsage()` 读该线程 session jsonl 尾部做实测；
3. 压缩提示改用真实来源百分比（无记录场景此前会显示"上下文已达 0%"）。

## v1.18.3：上下文长度可选（25/50/75/100%）

- 身份编辑里"思考强度"右侧新增"上下文长度"下拉：`模型默认` + `218k（25%）/436k（50%）/654k（75%）/872k（100%）`（按该模型最大长度折算，示例为 gpt-6.1-sol）。
- 存的是**具体 token 数**（`AgentProfile.contextWindow`），不是百分比；最大值来自 codex 目录（`codex debug models --bundled` 的 `max_context_window`，其次 `context_window`），拿不到时回落到内置家族表。
- 生效：codex `-c model_context_window=<N>`；claude 走我们自己的百分比与 rollover。徽标百分比、90% 换线程点、codex 自身压缩点统一按同一个 N。
- 校验：`8000 ≤ N ≤ 模型最大`，否则 `context_window_too_large` / `invalid_context_window`；"模型默认"= null，行为与 v1.18.2 一致。
